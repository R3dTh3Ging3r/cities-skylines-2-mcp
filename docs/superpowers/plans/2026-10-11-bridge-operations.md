# Bridge Operations and Recovery Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give every bridge mutation a recoverable outcome, bind work to the correct loaded world and player-control lease, and safely sequence bounded batches.

**Architecture:** Keep the existing loopback HTTP, main-thread handlers and native tool systems. `BridgeSystem` owns a managed operation registry, admission queue, world identity and lease; native adapters report apply/verification events back to it. Pure lifecycle policies are tested without Unity; native phase and save behavior are verified only in disposable fixtures.

**Tech Stack:** C# 9 / .NET Framework 4.7.2, existing game assemblies and dependencies, TypeScript ES2022/Node16, Node >=18, `node:test`, PowerShell and the linked-source core console runner.

**Spec:** [Bridge improvement delivery design](../specs/2026-10-11-bridge-improvements.md). Implements R02/R03 and the lifecycle/native-fixture portion of R12; depends on the foundation plan's contracts, client and test runner.

## Global Constraints

- All game/ECS reads and writes stay on the game thread. A batch performs sequential mutations, never parallel native construction.
- Preserve existing tool names and legacy success fields; add explicitly versioned contracts and documented deprecations. Correct false descriptions now; do not silently change a legacy field's unit or meaning.
- Keep the listener on loopback. No remote hosting, client allowlist expansion, or automatic machine-configuration edits are part of this plan.
- Compile the mod with `-p:SkipDeploy=true`. Deployment requires the game closed, a verified candidate, installed-build readback and a rollback copy.
- Native tests use a disposable city and a separately named verified checkpoint. Do not use the player's developed city as a test fixture.
- Keep raw game data, screenshots, saves, binaries, credentials and machine paths in ignored `.local/` paths. Use compact run IDs and paths below 240 characters.
- Preserve upstream history, attribution and unrelated work. Use focused `codex/` branches in the personal fork. No upstream messages or PRs without user instruction.
- A timeout is an unknown outcome, not cancellation; a successful placement, connected graph, good appearance and working service are separate checks.
- Use existing runtime dependencies. Core tests link BCL-only production sources into the foundation's net472 console runner; no Unity, game or JSON library references enter that runner. Retain reference-assembly package 1.0.3.
- Registry limit: 2,048 admitted operations per epoch, including completed keys, with no eviction permitting replay. Pending queue: 256. Batch limits: 32 mutation steps or 64 read items. Start at most one mutation/update; dispatch at most eight reads or 2 ms additional queued read work/update, whichever is reached first. A single native call cannot be preempted.
- New writer capabilities stay `unverified`/disabled until their G1 completion/lease fixtures pass. A specifically opted-in disposable native probe is validation, not general feature enablement.

## Review Focus

1. A response disappears after native apply: preserve the original operation ID and reconcile rather than retrying the placement — O2/O3.
2. The same save is reloaded while delayed rename, tile-refresh or screenshot work exists: reject old-world work before it touches the reloaded city — O2/O3.
3. A legacy caller arrives during takeover or another client's lease: immutable ingress identity and explicit legacy-write opt-in must not bypass the writer gate — O5.
4. A save task completes normally with `false`, or the intended artifact cannot be identified: report failure/uncertainty, never a verified checkpoint — O1/O4.
5. Queue saturation, user pause or a system-clock jump occurs during a run: keep stop/status responsive and do not resume or extend the run silently — O6/O7.

`WorldRef`, `CommandRequest`, `OperationRecord`, `MutationReceipt`, `Observation<T>` and `BridgeErrorData` use the shared spec, not alternate shapes. `operationId` is a caller-supplied UUID and the idempotency key. Hash canonical parsed arguments, command name and world; the lease must also be validated on admission/apply. Return the existing record only to a correctly scoped lookup/retry; changing arguments for an ID returns `IDEMPOTENCY_CONFLICT`.

**Legacy compatibility in O2/O5:** legacy requests cannot prove the world the caller originally observed. Release 2 disables legacy writes by default with `UPGRADE_REQUIRED`, leaving reads unchanged. Explicit local compatibility opt-in captures an immutable world at HTTP ingress from a main-thread-published managed snapshot; reject during an active v2 lease, loading, or a changed world before dispatch. If a caller supplies neither expected world nor operation ID, label this weaker path and `retrySafe:false`; do not present it as caller-observed fencing. No per-request auto opt-in or implicit lease after takeover.
